**Security lens, verdict: SIGN-WITH-CHANGE** (three named changes below). Suite: 18 passed. Probes run through Django's test client (temp file, removed; tree clean). The Lua script was also executed against a real Redis at localhost:6379 db 15: `[True, True, True, False, False]`, TTL 60, type zset; float scores and integer return behave as on fakeredis.

## Findings

**1. Fail-closed is unreachable when Redis stalls rather than refuses (required change)**
`metrics/redis_client.py:9` builds the client with no `socket_timeout` / `socket_connect_timeout` (verified live: both `None`, `retry=None`). `rate_limit.py:29-32` only reaches the 503 branch if `eval` raises. A Redis that accepts TCP and stops answering (or a black-holed route) blocks every worker thread in `redis.eval` indefinitely; no 503 is ever produced and the whole metered API stalls. This is pre-existing client config, but before this diff only public paths touched Redis; the diff puts every authenticated request on that path, so the docstring's policy claim ("Redis failure fails closed with a 503") is true only for a connection refusal. Refutation attempt: checked whether redis-py 8.1 applies a default timeout; it does not; `TimeoutError` is a `RedisError` subclass so the except clause would catch it once one can fire. Fix: set `socket_connect_timeout` and `socket_timeout` (sub-second, env-configurable) in `get_redis()` or via `REDIS_URL` query params, and add a test where the real client path raises `redis.TimeoutError` (the current outage test monkeypatches `allow`, so it never exercises `eval`; my probe with fakeredis `server.connected = False` confirmed the real path does yield 503 today).

**2. Trust-boundary precondition fails open silently on middleware misorder (required change)**
`rate_limit.py:24` uses `getattr(request, "tenant_id", None)`. `global_limit.py:18` uses `request.tenant_id`, which raises if auth has not run. Probe: moved `TenantRateLimitMiddleware` before `ApiKeyAuthMiddleware` via `override_settings`: 10/10 requests returned 200 against a limit of 3, zero Redis keys, no error. The default turns a config regression into an unmetered API with no signal. Fix: drop the getattr default (match `global_limit.py`), or add a test pinning `MIDDLEWARE.index(auth) < MIDDLEWARE.index(rate_limit)`. Preferably both; the first is a one-token change.

**3. `tiers.invalidate()` is per-process; the wave-2 hook's reader is a same-process dict (required change: fix the claim or the backend)**
`settings.py:37` selects `LocMemCache`; `tiers.py:24-26` deletes from it. Under any multi-worker WSGI deployment (the repo states no deployment model, so I am assuming the normal gunicorn shape), the admin endpoint's invalidation clears only the worker that served the admin request; the others serve the old limit for up to `CACHE_TTL_SECONDS` (60s). `test_admin_invalidation_takes_effect_without_waiting_for_ttl` proves this only in a single process. Security relevance: lowering an abusive tenant's limit is the incident-response lever and it lags up to 60s per worker. Bounded, so not a blocker. Note also that CONTRACT.md's context says Redis "is used for caching" while the diff introduces locmem. Fix, pick one: (a) `django.core.cache.backends.redis.RedisCache` on `REDIS_URL` (no new datastore; hot path stays zero-DB, gains one Redis round trip), or (b) keep locmem and rename the guarantee to "within CACHE_TTL_SECONDS across workers" in the docstring and test name so wave 2 does not build on a false premise.

**Precedence / wave-2 anticipation (verified, notes only)**
- Unlimited list is checked at `rate_limit.py:25` before `limit_for`, cache, DB, and Redis. Probe: a `tenant_tiers` row with `rate_limit=1` for `tenant-enterprise-01` was ignored (5/5 200s); zero Redis keys and zero `tenant_tiers` queries for that tenant. Contract satisfied. Consequences for wave 2: the admin endpoint writing a limit for an unlimited tenant is a silent no-op (it should reject), and because unlimited tenants are not counted, the wave-2(d) dashboard cannot show their usage. "Not enforced" vs "not counted" is a design choice worth recording now.

## Notes (no change required)
- **Key namespace overlap.** `ratelimit:{tenant_id}` (`windows.py:18`) shares a prefix with `ratelimit:global:{bucket}` (`global_limit.py:21`). Probe: a tenant_id of `global:<current bucket>` created a ZSET there and the next `/healthz` raised `ResponseError` (WRONGTYPE, uncaught, 500) for the rest of that window. tenant_id is operator-assigned, not attacker-controlled, so not a vulnerability; rename to `ratelimit:tenant:{id}` before keys go live, and it also keeps a future `ratelimit:tenant:*` scan clean.
- **Injection surfaces: clean.** Lua uses `KEYS`/`ARGV` only, no interpolation; `limit` is always an int (`tiers.py:19` handles NULL and preserves 0 correctly: `cached is not None`); request_id is uuid4 hex; tenant_id reaches Redis/cache from the `api_keys` row, not from the header. `limit <= 0` yields all-429, a sane "suspended" semantic.
- **Exempt-list env parsing** (`settings.py:45-47`, pre-existing): no `.strip()`; probe showed `"tenant-x, tenant-enterprise-01"` meters the enterprise tenant; a config typo violates "must not change behavior for unlimited-tier customers". Cheap to harden.
- **Fail-closed policy** is explicit and tested; the trade is that a Redis outage becomes a 503 for all metered tenants while unlimited and public traffic continue. Defensible; just be sure ops knows. Over-limit requests still cost the auth DB lookup per request (pre-existing ordering constraint).
- **Clock** is the app host's wall clock; inter-host skew shifts windows slightly per host. Bounded by NTP; `redis.call('TIME')` inside the script would remove it at the cost of the injectable-clock tests.

## Four absence checks
1. **Rollback:** remove the `MIDDLEWARE` line at `settings.py:19`; no migration; ZSETs self-expire within `window`; locmem dies with the process; the `CACHES` line equals Django's default. Clean.
2. **Coverage:** none-tenant, unlimited, under/over, sliding boundary, default, NULL row, 429 header, invalidation (single-process) all have tests. Gaps: real-client failure path (monkeypatched), timeout (finding 1), middleware order (finding 2). Cross-process invalidation is deferred as not testable in-process (finding 3).
3. **One owner:** `UNLIMITED_TIER_TENANTS` has one source; "public" is derived from `tenant is None` rather than a second copy of `PUBLIC_PATHS`; good. The `ratelimit:` prefix is hand-duplicated across `windows.py`, `global_limit.py`, and test literals; the middleware order is an unpinned implicit dependency.
4. **Bad day:** empty tenant_id `""` is metered under the shared key `ratelimit:` (operator data; the env comprehension correctly refuses to make `""` unlimited); duplicate keys for one tenant share a bucket (correct); concurrent arrivals are atomic in Lua with unique members; legacy NULL row and exempt tenant both tested and re-probed.

**Verdict: SIGN-WITH-CHANGE**: (1) Redis client timeouts plus a real-path timeout-to-503 test; (2) drop the `getattr` default and/or pin middleware order; (3) either move the tier cache to the Redis cache backend or restate the invalidation guarantee as TTL-bounded across workers.

## Findings

**1. The unlimited-tier list has no reader, contract DO-NOT #3 violated.** `acme_metrics/settings.py:43-45` defines `UNLIMITED_TIER_TENANTS`; `git grep` at HEAD shows the only occurrence is that definition. `metrics/middleware/rate_limit.py:18-26` enforces on every tenant unconditionally. Refutation attempted: checked whether enterprise tenants are protected some other way (a `TenantTier` row with a huge limit, an auth short-circuit): no; `tenant-enterprise-01` has no tier row, falls to `DEFAULT_RATE_LIMIT=100`, and the probe returned 429 on request #101. The contract's stated goal ("must not change behavior for existing unlimited-tier customers") is broken. Note the contract points at `acme/config.py`, which does not exist in this repo; the actual single owner is `settings.UNLIMITED_TIER_TENANTS`. Fix: at `rate_limit.py:19`, `if tenant in settings.UNLIMITED_TIER_TENANTS: return self.get_response(request)`; correct the contract pointer so nobody creates a second copy at `acme/config.py`; add the contract's evidence test #2.

**2. Live DB query on the hot path, contract DO-NOT #4 violated.** `rate_limit.py:30-34` `get_tenant_limit` does `TenantTier.objects.get(...)` per request with no cache (the inline comment `# DB read, see below` at line 19 acknowledges it; nothing below addresses it). Probe with `CaptureQueriesContext` after warm-up: 3 queries per request (`api_keys`, `tenant_tiers`, `metric_points`) versus 2 on `main` (`auth.py:21` + the view). Refutation attempted: looked for `lru_cache`, Django cache, or Redis-side caching of the limit: none. Fix: cache the tenant to limit lookup (Redis hash or process cache with TTL; Redis is the contract's sanctioned store), and add the contract's evidence test #3 (zero `tenant_tiers` queries after warm-up).

**3. A legitimate row shape crashes the middleware.** `metrics/models.py:16-17` documents `rate_limit` NULL as valid ("row exists but no limit was ever configured"), and `tests/conftest.py:25` seeds exactly that tenant. `rate_limit.py:25` `count > limit` raises `TypeError` when `limit is None`, HTTP 500 for `tenant-legacy` on its first request (probe confirmed). This is a behavior regression for an existing customer, which the contract's Goal forbids. Fix: decide the NULL semantic once (`DEFAULT_RATE_LIMIT` or unlimited) in the lookup function and test it; the fixture tenant already exists for this and no test uses it.

**4. Unauthenticated traffic is now limited twice, on a sentinel key, and `/healthz` gained a DB dependency.** `auth.py:15-17` sets `request.tenant_id = None` and passes public paths through; the new middleware runs anyway and builds `ratelimit:None:<window>` (probe: key present in fake Redis, `/healthz` returned 429 on call #101; one `tenant_tiers` query per `/healthz` call). Contract Context says the global limiter owns unauthenticated endpoints and DO-NOT #1 says leave that boundary alone; this adds a second, shared-bucket limiter in front of the same routes and couples the health probe to the database. The `@pytest.mark.django_db` added to `tests/test_auth.py:16` is the tell: it makes the test tolerate the new coupling instead of catching it. Fix: `if request.tenant_id is None: return self.get_response(request)`, deriving the public-path decision from auth's output rather than duplicating `PUBLIC_PATHS` (one owner); revert the `django_db` marker so `test_healthz_needs_no_key` again asserts the endpoint needs no DB.

**5. Fixed window shipped where the contract specified sliding, with no recorded amendment.** `metrics/ratelimit/windows.py:1-3` is a fixed bucket by design (docstring says so). Contract Wave 1(a) and Evidence #1 require the accepted rate to hold over *any* span of `WINDOW_SECONDS`. Probe: limit 3/60s, 3 requests at t=599.9 and 3 at t=600.1, 6 accepted in 0.2s. Refutation attempted: a fixed window is a defensible engineering trade, but the contract was reviewed by someone else before code and this branch neither meets it nor amends it. Fix: either implement sliding (sorted-set or two-bucket weighted) in the `metrics/ratelimit` package and add Evidence test #1, or amend `CONTRACT.md` explicitly with the reviewer's sign-off. Not the author's call to make silently.

**6. `INCR` then `EXPIRE` as two calls (`rate_limit.py:22-24`).** Probe: one failed `expire` leaves the key at TTL -1 and no later request ever sets it (`count == 1` guard). On re-check this is smaller than it first looks: the key embeds a monotonic window id, so a TTL-less key cannot lock a tenant out of future windows; the blast radius is a leaked key per incident, not a permanent 429. Still worth closing when the counter is reworked for finding 5 (pipeline with `expire(..., nx=True)`, or a Lua script). Note-level on its own.

**7. Module boundary: the counter algorithm does not live in the counter module.** Wave 1(a) created `metrics/ratelimit/` but put only key derivation there; the increment/expire/compare logic and the tier lookup (Wave 1(b)) both live inside the middleware (`rate_limit.py:18-34`). The middleware therefore owns three concerns (policy lookup, counter, HTTP enforcement) and the sliding-window change in finding 5 would have to edit the middleware rather than the package built for it. Fix: `ratelimit/counter.py` exposing `hit(tenant, now, window, limit) -> (allowed, count)`; `ratelimit/limits.py` for the cached lookup; middleware reduced to wiring.

**8. Coverage note (Quality will own this; recorded here because it's an absence).** `tests/test_rate_limit.py:19-23` asserts one 200 for a tenant with no tier row, which would also pass if the fallback returned any limit >= 1; it does not prove the default is used. None of the contract's three Evidence tests exist on the branch.

## Four absence checks

- **Rollback:** every forward step is reversible (remove `settings.py:19`, revert the `django_db` marker, delete two files); no migration, no schema change; counter keys self-expire within 60s except any leaked by finding 6 (harmless, `ratelimit:<tenant>:<window>` namespace does not collide with `ratelimit:global`). Adequate.
- **Coverage:** limit-from-row path: `test_under_limit_passes` / `test_over_limit_is_429`. `DoesNotExist` fallback: proxy test only (finding 8). NULL limit: no test. Unlimited list: no test. Window boundary: no test. Zero-DB hot path: no test. None-tenant path: no test (the modified healthz test hides it).
- **One owner:** unlimited list: owner is `settings.UNLIMITED_TIER_TENANTS`, zero readers (finding 1); contract names a file that doesn't exist. Public paths: owner is `auth.PUBLIC_PATHS`; the fix for finding 4 must derive from `request.tenant_id`, not copy the set. Limit values: owner is `tenant_tiers`; correct, but read live (finding 2).
- **The bad day:** `tenant_id=None`: shared sentinel bucket (finding 4). `rate_limit=NULL`: 500 (finding 3). Two first requests at once: `INCR` is atomic, one caller sets TTL; fine. Redis unavailable: exception, 500 for all authenticated traffic (fail-closed; `main` already fails closed for unauthenticated only). Contract is silent on fail-open vs fail-closed; flagging as a decision to record, not a defect. `RATE_LIMIT_WINDOW_SECONDS=0`: `ZeroDivisionError` per request; env-controlled, minor.

## Verdict

**BLOCK.** Named blocker: the unlimited-tier allowlist is defined and never read, so `tenant-enterprise-01` is throttled at request #101, a direct violation of contract DO-NOT #3 and of the Goal's "must not change behavior for existing unlimited-tier customers" (finding 1). Independently blocking on the same contract: the per-request `tenant_tiers` query on the hot path (DO-NOT #4, finding 2) and the 500 on a documented-valid NULL limit (finding 3). Findings 4, 5, 7 are required changes before re-review; 6 and 8 are notes to fold alongside.
